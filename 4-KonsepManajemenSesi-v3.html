1. Pengenalan Topik

Definisi

Manajemen sesi adalah mekanisme yang memungkinkan server mengingat pengguna tanpa autentikasi berulang. Jika manajemen sesi ini salah konfigurasi, penyerang dapat memakainya untuk menyamar sebagai pengguna. [1]

Mengapa Penting?

Session ID yang sudah terautentikasi setara dengan kredensial login. Jika bocor, penyerang dapat mengambil alih akun tanpa login maupun multi-factor authentication (MFA). [4]

Kegagalan autentikasi, termasuk kelemahan sesi, berada di peringkat ke-7 pada OWASP Top 10 2025. Hal ini meliputi ID sesi yang muncul di URL, penggunaan sesi yang sama waktu login dan tidak meng-invalidasi sesi saat logout ataupun timeout [5]

Tujuan Belajar

Melalui materi ini, diharapkan dapat memahami:

  1. Bagaimana sebuah sesi dibuat di sebuah aplikasi.
  2. Contoh penerapan manajemen sesi.
  3. Cara kerja manajemen sesi terautentikasi secara nyata melalui simulator.
  4. Cara mencegah, memperbaiki, dan praktik keamanan yang direkomendasikan.

2. Penjelasan Konsep

Kenapa Dibutuhkan?

Web mengirim data (teks, gambar, video) antara tampilan dan server menggunakan HTTP. HTTP bersifat stateless: server tidak mengingat interaksi sebelumnya, sehingga tanpa manajemen sesi pengguna harus login ulang di setiap halaman. Maka dari itu, diciptakannya Manajemen Sesi [2]

Cara Kerja

Kinerja dari sebuah sesi dimulai pada saat login.

  1. Saat pengguna login berhasil, server membuat Session ID yang unik. Session ID ini hanya pengenal; data pengguna tetap disimpan di server. [4]
  2. Front-end (Browser) menyimpan Session ID dan mengirimkannya pada setiap request, sehingga pengguna tidak perlu login lagi sampai logout.
  3. Sesi berakhir otomatis jika tidak aktif dalam waktu tertentu (idle timeout) atau sudah aktif terlalu lama (absolute timeout), untuk mencegah penyalahgunaan sesi yang ditinggalkan. [4]

Komponen dan Teknologi

  1. Session ID: pengenal acak yang menandai status autentikasi pengguna. Minimal berentropi 64 bit dan tidak mengandung informasi pengguna. [3][4]
  2. Session Lifetime: lama sesi boleh aktif sebelum pengguna harus autentikasi lagi.
  3. Cookie: file kecil di browser yang menyimpan Session ID.
  4. Web Server: membuat dan memverifikasi Session ID. Mode permissive menerima Session ID apa pun dari pengguna dan langsung membuat sesi dengannya; mode strict hanya menerima ID yang dibuat server sendiri. [4]
  5. Client: mengirim request dan menyimpan Session ID yang aktif.
  6. HTTP: protokol komunikasi klien-server yang tidak menyimpan state.

Contoh Implementasi

Bahasa pemrograman berbasis web juga memiliki sistem manajemen sesinya bawaannya seperti PHP, J2EE, ASP .NET, dan lain lain.
OWASP menyarankan memakai manajemen sesi bawaan framework dan bahasa pemrograman versi terbaru [4]

Tiga aspek penerapannya:

  1. Server-Side Session Token Storage: server menyimpan informasi sesi yang terkait dengan suatu Session ID.
  2. Used vs Accepted Session ID Exchange Mechanism: membedakan mekanisme pengiriman Session ID (Used) dan penerimaannya (Accepted). Setelah login, server mengirim Session ID melalui cookie. Pada request berikutnya, server hanya menerima Session ID dari cookie dan menolak cara lain, misalnya parameter URL.
  3. Transport Layer Security (HTTPS/TLS): mengenkripsi komunikasi klien-server untuk melindungi Session ID.

Ancaman & Risiko

  1. Session Hijacking: penyerang memakai Session ID valid yang dicuri atau ditebak untuk menyamar sebagai pengguna. Ini mungkin terjadi karena autentikasi hanya dilakukan saat login. [6]
  2. Session Sniffing: penyerang menyadap jaringan untuk membaca Session ID atau cookie yang dikirim tanpa enkripsi. [6]
  3. Man-in-the-Middle: berbeda dengan sniffing, penyerang berada di antara klien dan server sehingga dapat membaca dan mengubah komunikasi untuk mendapatkan Session ID. [6]
  4. Session Fixation: penyerang menanamkan Session ID yang sudah ia ketahui pada sebuah link dan meminta korban login lewat link tersebut, sehingga ID itu terikat dengan akun korban. Serangan berhasil jika server tidak membuat Session ID baru setelah login. [6]
  5. XSS: penyerang menjalankan JavaScript di browser korban. Berbahaya jika token (misalnya JWT) disimpan di localStorage atau sessionStorage karena dapat dibaca oleh skrip. [6]

    5. Pencegahan, Perbaikan & Rekomendasi

    Pencegahan

    1. Gunakan atribut HttpOnly, SameSite, dan Secure pada cookie.
    2. Kirim cookie autentikasi hanya melalui HTTPS.
    3. Terapkan defense-in-depth: beberapa lapis perlindungan yang bekerja bersama.
    4. Beri batas waktu sesi yang tepat (tidak terlalu lama dan tidak terlalu singkat).
    5. Gunakan Session ID yang panjang dan berentropi cukup.

    Perbaikan

    1. Buat Session ID baru setelah login (mencegah Session Fixation) dan edukasi pengguna tentang link serta pesan phishing.
    2. Gunakan koneksi terenkripsi dengan HSTS (membantu mencegah Man-in-the-Middle dan Session Sniffing).

    Rekomendasi OWASP

    1. Jika harus membuat Session ID sendiri, gunakan CSPRNG (pembangkit angka acak semu yang aman secara kriptografi) dengan ukuran minimal 128 bit, dan pastikan setiap ID unik. [4]
    2. Jangan simpan token sesi di localStorage atau sessionStorage. [4]
